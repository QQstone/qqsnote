# Python 学习路线重写设计

## 背景与目标

现有 `source/_posts/PythonMachineLearningFoundation.md` 把 Python 学习重点放在 NumPy、Pandas、机器学习和深度学习库，部分表述要求“精通”，但没有结合作者已有的 11 年 Web/full-stack 经验、机器人软件转型方向、每周可投入时间以及 AI 辅助编程带来的工作方式变化。

本次重写将该文章定位为 Python 学习总入口，服务于以下目标：

- 在每周 5～7 小时投入下，规划可持续的 3 个月和 6 个月学习路线。
- 达到资深全栈工程师转向机器人应用软件、工业视觉和 AI 应用岗位所需的 Python 工程能力。
- 覆盖面试中真正影响通过率的语言基础、工程判断、代码阅读和故障分析，不追求完整背诵冷门语言机制。
- 建立使用 AI 生成代码、审查风险并用测试和运行证据验证结果的工作闭环。
- 用可检查的项目产物证明能力，而不是用笔记数量或知识点清单代替实践。

## 范围

本次只重写 `source/_posts/PythonMachineLearningFoundation.md`。原有 `BasicPython-*`、`PythonOOP.md`、`NumPy.md`、`Pytorch.md` 等文章保留为历史专题笔记，不进行系统修订。新文章可链接相关专题，但不能依赖旧文章才能理解主路线。

文章面向已有资深软件工程经验、Python 熟练度仍需提升的读者，不按零基础语法教程组织。内容以 Python 3 的现代工程实践为准，但避免绑定容易过时的精确版本号和工具宣传。

## 内容结构

### 1. 定位与取舍

开篇先给结论：Python 是连接 ROS2、视觉算法、AI 模型、设备 SDK 和工程服务的工具。目标不是成为语言特性专家，而是能够读懂、修改、测试、部署并对 Python 系统负责。

说明 Vibe Coding 改变的是代码生产成本，不是正确性、可靠性和安全责任。文章不把“全部手写”和“全部交给 AI”设为二选一。

### 2. 能力分层

使用四层表格区分学习深度：

1. 必须闭卷掌握：常用数据结构、函数和作用域、可变性、异常、迭代、资源管理、模块、类型提示、基本并发边界。
2. 需要工程化掌握：项目结构、依赖与配置、日志、pytest、静态检查、API/数据边界、超时与取消、可观测性。
3. 按目标岗位掌握：NumPy/OpenCV、FastAPI/Pydantic、ROS2 Python 客户端、PyTorch 推理或训练基础。
4. 可以借助文档或 AI：冷门标准库 API、元类和描述符细节、复杂装饰器、少见框架参数、版本相关行为。

每层说明掌握标准和验证方式，防止“知道名词”等同于“能够交付”。

### 3. 面试范围

保留高收益基础题，但每个主题连接到真实故障或设计选择：

- `list`/`tuple`/`dict`/`set` 的语义、复杂度和选型。
- 引用、浅拷贝、可变默认参数和参数传递。
- 迭代器、生成器和上下文管理器的流式处理与资源释放价值。
- 异常边界、异常链、日志与错误恢复。
- GIL 的适用范围，以及线程、进程和 `asyncio` 对 I/O 与 CPU 任务的选型。
- 类型提示的静态边界，以及外部数据仍需运行时校验。
- pytest 的单元测试、边界测试、替身使用和集成测试取舍。

不展开以记忆冷知识为目的的输出题、手写元类、解释器源码函数名和复杂算法题集。算法训练只保留目标公司筛选所需的数组、哈希、栈队列、树遍历、二分和基本复杂度分析。

### 4. AI 协作开发

文章给出可执行的 AI 协作闭环：

1. 提供明确任务、输入输出契约、约束、现有代码和验收标准。
2. 让 AI 先给方案、风险和测试，再生成小批量改动。
3. 人工审查数据边界、错误处理、资源生命周期、并发、依赖、安全和硬件副作用。
4. 通过格式化、静态检查、单元测试、集成测试和真实运行验证。
5. 保留关键决策、失败案例和验证结果，用于复盘与面试表达。

明确禁止未经验证直接接受的代码类型：设备控制、文件删除、数据库迁移、认证授权、并发共享状态、模型输入输出转换以及涉及真实机器人动作的逻辑。

### 5. 时间路线

按每周 5～7 小时给出两阶段路线：

- 0～3 个月：补齐 Python 工程底座，完成一个可测试的设备/视觉数据服务。
- 3～6 个月：接入 OpenCV 或 ROS2 模拟数据，补齐状态建模、并发、可观测性和部署说明。

建议每周时间分配为：2 小时语言与面试基础、3 小时项目、1 小时 AI 代码审查与测试、0～1 小时复盘。面试前再根据岗位描述短期提高基础题比例，不长期维持刷题模式。

### 6. 贯穿项目

使用“视觉检测与设备状态服务”作为最小主项目。项目包含：

- 从目录、摄像头录制文件或模拟消息读取图像与设备状态。
- 用 OpenCV 完成一个可解释的检测或标定流程，不要求训练大型模型。
- 用 Pydantic 定义外部数据边界，用 FastAPI 暴露状态、任务和结果接口。
- 记录结构化日志、错误和耗时，支持配置、超时、取消和有限重试。
- 使用 pytest 覆盖核心转换、异常路径和 API 契约。
- 提供 README、架构图、运行命令、测试结果、演示视频或截图、已知限制和失败案例。

该项目保持硬件可选：没有机器人或相机时可用录制数据与模拟设备完成。后续可以接 ROS2 topic/service/action，但主路线不依赖真实硬件。

## 交付物与验收标准

正文完成后应满足：

- Hexo front matter 有有效标题、日期、标签和分类。
- 文章清楚区分闭卷掌握、工程掌握、按岗位掌握和可查询内容。
- 包含 3 个月、6 个月路线以及每周 5～7 小时分配。
- 每个项目阶段包含交付物、验收标准和面试价值。
- 至少包含一个 AI 生成代码的审查示例，展示风险、修正和验证方式。
- 明确列出低优先级和暂不学习内容。
- 不宣称作者已具备没有项目证据支持的生产机器人、控制算法或模型训练能力。
- 不使用“必须精通所有 NumPy/PyTorch”等脱离目标岗位的绝对表述。
- Markdown 结构可读，代码示例短小、可运行或明确标注为伪代码。
- `npm run build` 成功完成。

## 非目标

- 不把文章扩写成完整 Python 语法手册。
- 不系统讲解机器学习数学、深度学习训练或 VLA 研究。
- 不承诺仅通过半年学习即可胜任机器人控制算法或具身智能研究岗位。
- 不批量修改其他 Python 历史笔记或 Hexo 主题。
- 不为了展示 AI 工具而加入与项目交付无关的提示词合集。

## 风险与控制

- 内容过宽：用主项目和目标岗位筛选主题，无法直接服务项目、面试或故障定位的内容降级为查询项。
- 文章过长：优先使用表格、清单和小型示例；详细 API 放到现有专题或官方文档。
- 工具快速变化：强调工作流与验收证据，不把某个 AI IDE 或依赖管理器写成唯一选择。
- 项目变成 Web 舒适区：验收必须包含 OpenCV、ROS2 模拟数据或坐标/设备状态中的至少一项机器人领域证据。
- 面试准备不足：保留高频语言基础和有限算法训练，但要求用机制、边界和项目故障回答，避免只背结论。
