# 前端性能与测试指南重写设计

## 背景与目标

现有 `source/_posts/forntend-performance.md` 只有早期 RAIL、性能指标和少量优化提示，其中 FID 等指标已经需要更新；`source/_posts/WebTest.md` 只有 front matter，尚未形成测试方法论。Jasmine 和 Angular 测试专题保留了历史工具用法，但不适合承担现代前端测试总入口。

本次重写面向已有 11 年 Web/full-stack 经验、正在转向工业可视化和机器人应用软件的资深工程师。目标不是罗列更多优化技巧或测试框架 API，而是建立两套可复用的工程决策方法：

- 性能问题能够从用户影响出发，经过测量、定位、实验和回归验证形成证据链。
- 测试策略能够从业务风险出发，选择最低成本且足以发现目标故障的测试层级。
- AI 智能体用于生成、执行、收集和初步归类，工程师保留目标、测试预言、因果判断、发布门槛和安全边界的责任。
- 面试准备聚焦诊断过程、工具选择、取舍和项目证据，不长期背诵浏览器阶段、工具参数或固定分数。

## 性能篇设计

### 1. 先建立性能责任边界

开篇说明 Vibe Coding 降低了写优化代码和运行工具的成本，但 AI 不能替代以下判断：真实用户是否受影响、指标阈值来自什么业务目标、trace 能否支持因果结论、优化是否引入正确性和可维护性风险。

使用三级掌握标准：

1. 必须闭卷掌握：关键渲染路径概念、主线程阻塞、网络与缓存、布局绘制、内存生命周期、测量先于优化。
2. 会使用工具验证：Chrome DevTools、Performance、Network、Memory、Lighthouse、Web Vitals、bundle 分析和框架 Devtools。
3. 可由 AI 初步完成：批量审计、trace 摘要、bundle 差异、实验脚本、候选假设和报告初稿；结果必须人工复核。

### 2. 更新指标体系

Core Web Vitals 使用 LCP、CLS 和 INP，明确 FID 已被 INP 替代。辅助指标覆盖 TTFB、FCP、TBT、Long Task、帧率、内存和业务自定义指标。

区分：

- Field/RUM 数据回答真实用户、设备和网络下发生了什么。
- Lab 数据用于可重复诊断、对比和 CI 回归。
- Lighthouse 分数是综合信号，不是业务性能的唯一真相。

阈值以官方建议作为通用参考，但项目预算需要结合用户、设备、网络、交互和业务风险确定，不把某个示例数字写成普适 SLA。

### 3. 建立分层诊断流程

固定顺序为：定义用户问题和场景 -> 建立基线 -> 录制证据 -> 定位主要瓶颈 -> 提出一个可证伪假设 -> 做最小改动 -> 同环境复测 -> 加入回归守卫。

诊断层级包括：

- 服务端、网络、缓存和压缩。
- HTML/CSS/JavaScript/字体/图片加载及优先级。
- JavaScript 执行、Long Task、事件处理和 Worker 边界。
- 框架响应式、组件更新、DOM 数量和状态所有权。
- style/layout/paint/composite 与动画。
- 内存泄漏、事件监听、定时器、订阅和资源释放。
- Canvas/WebGL 的渲染频率、对象分配、纹理/几何体、draw call 和 GPU 资源释放。

### 4. 加入工业状态看板和 Web3D 场景

使用高频设备遥测场景说明接收频率与展示频率分离、有界缓冲、报警与状态更新的不同可靠性策略、对象复用、视口裁剪、资源释放和故障回放。优化必须给出数据量、设备、采样周期和验收指标。

### 5. 面试与实践

面试题围绕：从白屏、交互延迟、滚动卡顿、内存增长、Web3D 掉帧中如何定位；如何区分网络、主线程、布局绘制和 GPU 问题；为什么不能只看 Lighthouse；如何证明优化有效。

实践任务为“工业状态看板性能治理”：提供基线报告、trace、瓶颈假设、两项最小优化、回归预算、前后数据、失败实验和面试复盘。

## 测试篇设计

### 1. 从风险而不是框架开始

测试策略先回答：哪些失败最昂贵、在哪一层最容易稳定发现、发布前需要什么证据。避免把测试金字塔、测试奖杯或覆盖率当作脱离项目的教条。

使用三级掌握标准：

1. 必须闭卷掌握：测试边界、可观察行为、测试预言、隔离与替身、异步测试、稳定性和失败定位。
2. 会使用工具验证：TypeScript/ESLint、Vitest/Jest、Testing Library、MSW 或 adapter、Playwright/Cypress、契约/视觉/无障碍/性能测试。
3. 可由 AI 初步完成：用例与 fixture 初稿、边界数据、E2E 脚本、失败聚类、覆盖缺口建议和维护性检查；关键断言与发布门槛由工程师确认。

### 2. 建立风险到测试层级的映射

文章按故障选择工具：

- 静态检查发现类型、规范和部分错误模式。
- Vitest/Jest 验证纯逻辑、状态机和模块契约。
- Testing Library 验证用户可见的组件行为，Vue/React 仅作为辅助示例。
- MSW 或 adapter 隔离网络/SDK 边界，同时保留协议形状。
- Playwright/Cypress 验证少量关键用户流程和真实浏览器集成。
- 契约、视觉回归、无障碍、性能回归按项目风险增加。

工具比较只覆盖选型边界：Vitest 与 Vite 生态集成更直接，Jest 生态和既有项目基础广；Playwright 的多浏览器与上下文能力适合现代 E2E，Cypress 的交互调试体验和既有生态仍有价值。文章不宣称单一工具在所有项目中最佳。

### 3. 覆盖资深工程问题

重点包括：测试公共行为而不是私有实现；少量稳定替身；假计时器和异步任务边界；稳定 selector；数据和环境隔离；flaky test 的归因与治理；覆盖率只能发现未执行代码，不能证明断言质量；CI 按速度和风险分层。

加入工业/机器人前端边界：状态机、权限、命令确认、断连重连、乱序/重复消息、报警不可丢失、WebSocket 数据校验、WebGL canvas 非空与关键交互。真实设备副作用不能由普通 E2E 测试无门控触发。

### 4. AI 生成测试审查案例

示例展示一组“覆盖率很高但价值很低”的 AI 测试：只断言组件存在、私有方法被调用和实现细节快照。审查后改为用户行为、错误边界、状态变化和协议结果断言，并说明 AI 无法从缺失需求中自动发明可信测试预言。

### 5. 面试与实践

面试题围绕：如何测试一个组件、如何选择单元/集成/E2E、Mock 何时有害、如何治理 flaky test、覆盖率为何不等于质量、AI 生成测试怎样审查。

实践任务为“关键工作流测试治理”：选择设备状态页或视觉任务页，建立风险表，补充纯逻辑、组件和一条 E2E 测试，加入断连/超时/重复消息失败用例，并输出 CI 分层、失败报告和 AI 审查记录。

## 两篇文章的连接方式

两篇文章互相使用 Hexo `post_link` 链接。性能篇把性能预算和回归守卫指向测试篇；测试篇把性能回归的指标、实验和 trace 解释指向性能篇。内容不重复展开同一工具教程。

两篇文章都包含：三级掌握标准、AI 与人工责任表、面试问题、实践交付物、验收标准、面试价值、自检清单和“不死磕”内容。

## 验收标准

- 两篇文章的 front matter 有有效标题、原日期、更新时间、标签和分类。
- 性能篇明确使用 LCP、CLS、INP，并说明 FID 已被替代。
- 性能篇区分 Field/RUM、Lab 和 Lighthouse，给出分层诊断流程。
- 性能篇覆盖工业状态看板与 Canvas/WebGL，并要求前后证据和回归预算。
- 测试篇覆盖静态检查、Vitest/Jest、Testing Library、MSW/adapter、Playwright/Cypress 以及按风险选择的专项测试。
- 测试篇解释测试预言、Mock、异步、flaky test、覆盖率和 CI 分层。
- 两篇文章均明确 AI 可完成的机械工作与必须人工决策的边界。
- 至少包含一个 AI 生成测试的审查案例。
- 每篇均有实践交付物、验收标准和面试价值。
- 不批量修改历史框架专题，不引入新依赖。
- `npm test` 与 `npm run build` 成功。

## 非目标

- 不写浏览器规范、Chrome DevTools 或测试框架的完整教程。
- 不背诵所有渲染流水线阶段、测试 matcher 和 CLI 参数。
- 不把固定 Lighthouse 分数、覆盖率或 E2E 数量当作通用质量标准。
- 不宣称 AI 能独立确定性能根因、测试预言、硬件安全边界或发布责任。
- 不把前端性能优化简化为资源压缩，也不把测试简化为单元测试数量。

## 风险与控制

- 工具快速变化：强调稳定的诊断和测试原则，工具只说明当前选型边界并优先链接官方文档。
- 两篇文章过长：详细 API 留给官方文档或历史专题，正文只保留决策、最小示例和项目证据。
- 与现有面试指南重复：两篇负责专题方法和实践，跨主题职业投入继续由综合面试指南负责。
- AI 内容流于口号：每篇都要求具体输入、输出、人工复核点和验证证据。
- 项目退回普通 Web CRUD：工业遥测、Web3D、设备状态或视觉工作流至少选择一项作为实践对象。
