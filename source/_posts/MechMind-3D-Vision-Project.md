这篇笔记按“机器人 + Mech-Eye 3D 相机”的真实集成项目来组织。目标不是背厂商参数，而是能够说明：设备为什么这样选、数据怎样从相机到机器人、标定和验证如何做、出现问题时怎样定位。

## 1. 先把产品边界说清楚

一个容易被追问的基本问题是“你们用的是 Mech-Mind 还是 Mech-Vision？”建议先拆开：

| 名称 | 在系统中的角色 |
| --- | --- |
| Mech-Mind | 厂商和产品品牌 |
| Mech-Eye SDK | 访问 3D 相机的原生 SDK，负责发现、连接、参数、采集和数据读取 |
| Mech-Vision | 视觉工程软件，负责采集编排、点云处理、分割、匹配、定位和检测 |
| Mech-Viz | 机器人路径/抓取规划和碰撞规避软件 |
| Agilebot GBT-C16A | 六轴协作机器人本体及控制柜，负责运动、I/O 和安全状态 |

EPI项目 直接调用 `Mech-Eye SDK`，准确的描述是“集成 Mech-Eye 相机 SDK”；这不等同于“集成了 Mech-Vision”。如果 Mech-Vision 独立运行，则需要通过 TCP/HTTP 或厂商接口交换视觉结果，并明确谁负责采集、谁负责推理、谁负责机器人执行。

## 2. 设备与选型：参数要能落到工程决策

资料中的组合是 Agilebot GBT-C16A + Mech-Eye NANO ULTRA-GL。参数不是孤立的，作为经验而言时要说明它们如何影响安装和节拍。

### 2.1 机器人侧

- C16A 是六轴协作机器人，额定负载 16 kg，工作半径约 980 mm，位置重复定位精度约 0.03 mm。
- 最大 TCP 速度资料标为 2.5 m/s；实际应用速度还要受负载、姿态、安全设置、视觉采集时机器人必须停止等条件约束。
- 末端工具端与控制柜 I/O 是两套资源。视觉触发、夹爪控制和安全互锁要先确定走工具端 I/O、控制柜 I/O 还是网络协议，再分配点位和电平。
- 末端负载预算不能只算相机 0.7 kg，还要加支架、线缆、夹具和偏心力矩；相机安装会改变 TCP、惯量和碰撞风险。

### 2.2 相机侧

NANO ULTRA-GL 是蓝光结构光 3D 相机，2D 图像为单色，输出深度图、XYZ/Range 数据和带强度纹理的点云。资料中的典型参数为：

- 2D/深度分辨率 2400 x 1800。
- 两档工作距离：250--500 mm、400--800 mm；对应 FOV 和安装空间不同，不能把两套数据混用。
- 典型采集时间约 0.5--0.9 s，正式节拍必须在目标材质、曝光参数和网络环境下实测。
- 资料给出约 0.1 mm 的 VDI/VDE 测量精度，以及 0.045 mm @ 0.4 m、0.1 mm @ 0.6 m 的单点 Z 值重复性。它们是规定测试条件下的指标，不是任意工件、任意姿态下的绝对抓取误差。
- 相机重量约 0.7 kg，供电 24 VDC、峰值电流约 3.75 A，Gigabit Ethernet，IP65；安装面平面度资料要求约 +/-0.05 mm。
- 设备有 24 V 和 Ethernet 端口，硬件手册未列独立 DI/DO 触发端子。工程上优先采用 SDK/GenICam 软件触发；若工艺要求硬件触发，必须在采购和现场方案阶段确认附件与版本。
- 相机建议预热约 30 分钟后再做精度验收。蓝光结构光对反光、透明、黑色表面和环境光敏感，必要时要调整曝光、HDR、滤波或工件表面处理。

作为经验而言不能只说“精度 0.1 mm”。更完整的说法是：“我会先按工作距离选 FOV，再用现场材质和节拍验证点云有效率、重复性和机器人落点误差，最后把误差预算拆成相机、标定、机器人重复性、夹具和工件定位几部分。”

## 3. 推荐系统拓扑与数据契约

```text
GBT-C16A 控制器 <---- TCP/IP / Modbus TCP / Agilebot SDK ----> 工控机
       |                                                         |
       +---- 夹爪、到位、互锁 I/O                                  +---- Mech-Eye SDK
                                                                     |
                                                         2D / depth / XYZ point cloud
                                                                     |
                                              ROI -> 去噪 -> 分割/匹配 -> 位姿与质量分数
                                                                     |
                                      手眼变换 + 工具偏置 + 安全检查 -> 机器人目标位姿
```

系统接口要先约定数据契约，而不是等到联调时再猜：

```text
frame_id       相机坐标系、机器人基座、工具/TCP、工件坐标系的命名
unit           点云通常为 mm；机器人位姿接口可能要求 mm 或 m，必须统一
timestamp      采集时间、机器人位姿时间；用于判断运动期间采集和结果过期
validity       无效深度/NaN/遮挡点的表示方式
point_format   XYZ、XYZ+Intensity、法向量、颜色映射等字段及排列
pose           平移 + 旋转表示（矩阵、四元数或欧拉角）和旋转顺序
quality        匹配分数、有效点比例、残差、置信度和失败原因
```

相机原始点云单位通常是毫米。EPI项目的适配器还要做坐标轴约定转换；如果驱动层已经完成传感器坐标修正，业务层不能再凭经验翻转 Y/Z 轴。最常见的灾难性错误是单位缩放一次、坐标翻转两次，结果看起来“方向差不多”但机器人落点完全错误。

## 4. SDK 集成的必要知识

### 4.1 从安装到运行

Mech-Eye SDK 是 C/C++ 原生 SDK，不是 Rust crate。EPI项目的典型链路是：

```text
libMechEyeApi.so
  -> mechmind-sys（C++ wrapper + FFI）
  -> camera-service（MechMindAdapter）
  -> runtime-service 的 camera_3d 设备
  -> HTTP/WS、调试台或视觉 pipeline
```

Linux 约定安装目录为 `/opt/mech-mind/mech-eye-sdk`，也可通过 `MECHMIND_SDK_DIR` 指定。构建和运行时都要考虑头文件、动态库和运行时搜索路径：

```bash
export MECHMIND_SDK_DIR=/opt/mech-mind/mech-eye-sdk
cargo build -p runtime-service --features mechmind
ldd target/debug/runtime-service | grep -i mech
export LD_LIBRARY_PATH="$MECHMIND_SDK_DIR/lib:$LD_LIBRARY_PATH"
```

运行时配置至少要能表达设备类型、品牌和 IP：

```toml
[[devices]]
id = "camera-3d-1"
type = "camera_3d"
brand = "mechmind"
ip = "192.168.111.20"
```

`runtime-service` 的 `mechmind` feature 会转发到 `camera-service` 和 FFI crate。只写 `brand = "mechmind"` 而没有编译 feature，通常只能得到“不支持的设备品牌”，不会创建真实驱动。

### 4.2 采集调用应如何设计

SDK 调用可能是阻塞式的。服务层要把发现、连接、采集、断开和参数设置包装成明确的状态机，并把阻塞调用移到专用线程或 `spawn_blocking`，避免卡住 Tokio/HTTP/WS 事件循环。一个可复述的抽象流程是：

```text
Disconnected
  -> Discovering
  -> Connected
  -> Configured
  -> Capturing
  -> DataReady / CaptureFailed
  -> Connected 或 Reconnecting
```

需要记录相机 IP、SDK/固件版本、曝光/增益、触发模式、采集耗时、点云有效率、错误码和重连次数。相机被 Mech-Eye Viewer、Mech-Vision 或其他进程占用时，发现成功也可能无法采集，不能只看 ping。

资料整理中提到的离线 SDK 包为 2.5.4，官方材料要求 Mech-SDK >= 2.3.3；下载中心资料版本可能更新到 2.6.0。正式项目应锁定 SDK、相机固件和 Mech-Vision（若使用）的兼容矩阵，在测试机先验证发现、连续采集、点云格式和升级流程。

## 5. 从一帧点云到机器人位姿

一个可解释的视觉抓取/定位 pipeline 通常是：

1. 机器人移动到安全观测位，确认速度为零、夹具和安全互锁满足条件。
2. SDK 触发采集，检查图像/深度/点云时间戳和有效点比例。
3. 按工作区域做 ROI、体素降采样、统计滤波或半径滤波；滤波参数要以目标尺寸和点间距为依据。
4. 对工件做平面去除、聚类、模板匹配、特征/边缘提取或模型拟合，输出目标位姿和质量分数。
5. 将相机坐标系中的结果通过手眼变换转换到机器人基座/工件坐标系，再叠加 TCP 和夹具偏置。
6. 做关节限位、姿态可达性、奇异位形、碰撞区和抓取方向检查；失败时回到安全位，不把低置信度结果直接下发。
7. 机器人执行 MoveJ/MoveL 或控制器支持的轨迹，读取到位、夹取和报警反馈，再决定下一状态。

核心关系可写成：

```text
T_base_target = T_base_camera * T_camera_target
T_base_tcp    = T_base_flange * T_flange_tcp
```

实际项目还要明确矩阵左乘/右乘约定、旋转方向、时间同步和工具坐标定义。不要把 `T_camera_target` 当成“相机输出的 XYZ 三个数”就直接使用：目标姿态还需要法向、主轴、模板坐标或工艺定义。

## 6. 手眼标定与验收

### 6.1 先区分两种安装

- Eye-in-Hand：相机装在机器人末端。相机随机器人移动，适合从多个视角观察；需要求解相机与法兰/TCP 的固定变换。
- Eye-to-Hand：相机固定在外部支架。相机不随机器人移动，需要标定相机与机器人基座/工件坐标系的关系。

当前笔记中的 `AX=XB`（Tsai-Lenz）属于手眼标定的数学表达，但工程上还必须说明采样姿态、标定板/特征检测、机器人位姿来源和残差验证。建议采集覆盖不同位置和姿态的多组样本，避免所有姿态近似共面或绕同一轴小角度变化。

验收至少包含：

- 重投影/特征检测误差和手眼求解残差。
- 标定板或已知工件在不同机器人姿态下转换到基座坐标后的散布。
- 重复采集、重复运动后的落点误差和姿态误差。
- 工作空间边缘、不同距离、不同表面材质下的有效率。
- 机器人停止后采集与运动中误触发的时序检查。

如果误差突然变大，按“单位 -> 坐标轴 -> 标定姿态 -> TCP/法兰 -> 机器人位姿时间 -> 夹具刚度 -> 点云质量”的顺序排查。重新标定不是第一反应；先保存原始点云、机器人位姿、参数和版本，确保问题可复现。

## 7. 网络、电气与安全

推荐相机直接连接工控机；经过交换机时使用至少 1 Gbps、CAT5e 以上屏蔽网线，并验证连续采集不丢帧。相机 24 V 电源按峰值约 3.75 A 和线缆压降选型，不能只按平均功耗 12 W 估算。

机器人控制器可通过 TCP/IP、Modbus TCP、RS485 或 Agilebot SDK 通信。网络通信解决的是命令与状态交换，不替代安全回路：急停、使能、保护停止、门禁和夹爪互锁应由控制器/安全系统实现。视觉结果只能作为“允许执行”的一个条件，不能让 LLM 或普通业务服务直接绕过安全状态下发运动命令。

## 8. 常见故障的定位顺序

| 现象 | 优先检查 |
| --- | --- |
| 编译找不到头文件 | `MECHMIND_SDK_DIR`、`include/` 是否完整、SDK 架构是否匹配 |
| 链接找不到 `libMechEyeApi.so` | SDK `lib/`、链接参数、x86_64/ARM 架构 |
| 编译成功但启动失败 | `ldd`、`LD_LIBRARY_PATH`、rpath、容器内动态库 |
| 发现不到相机 | IP/子网、防火墙、网卡、交换机、相机电源和 SDK 兼容性 |
| 能发现但不能采集 | 被其他软件占用、参数/触发模式、固件兼容性、目标材质和曝光 |
| 点云方向或尺寸错误 | 单位、轴约定、矩阵乘法顺序、驱动层是否已经做坐标修正 |
| 机器人落点偏差大 | 手眼/TCP、机器人位姿时间、支架刚度、工件定位、点云质量 |
| 偶发抓取失败 | 记录原始数据和质量分数，检查运动未停止、反光遮挡、超时和重连 |

## 9. 作为经验而言叙述模板：把经历讲成闭环

可以按“目标--架构--难点--验证--边界”回答，而不是只报型号：

> 项目用 Agilebot C16A 搭配 Mech-Eye NANO ULTRA-GL 做机器人 3D 定位。相机通过 Gigabit Ethernet 接入工控机，服务层用 Mech-Eye SDK 完成发现、连接、参数配置和点云采集；机器人侧通过控制器 SDK/TCP 或 Modbus 读取位姿、下发运动并接收 I/O 状态。视觉 pipeline 对点云做 ROI、滤波和目标定位，再通过 Eye-in-Hand/Eye-to-Hand 标定结果把目标从相机坐标转换到机器人基座坐标，经过质量分数、关节可达性、碰撞和安全状态检查后才执行。我们用重复采集、不同姿态和现场材质做验收，记录采集耗时、有效点率、标定残差和最终落点误差。SDK 原生调用和现场机械/电气验收由对应模块负责，我负责的是服务集成、数据契约、状态流转、可观测性和联调验证。 

最后一句很重要：如果没有亲自完成某一环节，应明确说“我理解接口和验收方法，但这部分不是我独立负责的”。这比笼统声称“做过 Mech-Mind 项目”更可信。

## 10. 需要补齐的可验证证据

当前资料足以形成作为经验而言的知识框架，但不能单独证明已经完成生产项目。最小可展示证据建议是：

1. 在测试机完成一次真实相机发现、连接和连续采集，保存 SDK/固件版本、点云样例和日志。
2. 做一个六轴机器人数字孪生或 ROS2/Web 调试台，展示相机帧、机器人状态、TF 和目标位姿。
3. 用标定板或已知工件完成一套手眼标定，给出残差、重复性和失败案例。
4. 建立一个可回放的视觉状态机：采集失败、点云低质量、机器人报警和超时都能进入安全恢复路径。
5. README 写清数据单位、坐标系、触发时序、误差预算、测试方法和未覆盖范围，并附一段端到端演示视频。

这些产物能把“读过 Mech-Mind 资料”推进为“能构建和验证机器人视觉软件系统”。

## 11. 高精度表面重建：双目、结构光与激光线扫怎样选择

如果只比较表面重建精度，通常可以粗略理解为：

```text
激光线扫 > 结构光面阵 > 普通被动双目
```

这个排序不是绝对的。最终精度还取决于工作距离、视野、目标材质、标定、运动精度、时间同步和多站拼接方法。尤其要注意，“双目”和“结构光”不是完全互斥的分类：有些设备用两个接收镜头加主动投影器，本质上属于主动双目结构光；判断具体相机时应看其深度成像模式，而不能只数镜头数量。

### 11.1 普通双目视觉

普通双目像人的两只眼睛：左右相机从不同位置观察同一个点，根据该点在两张图像中的横向位置差（视差）反推距离：

```text
Z = f * B / d
```

其中 `Z` 是深度，`f` 是焦距，`B` 是左右镜头基线，`d` 是视差。再结合相机内参，可把像素位置转换为空间坐标：

```text
X = (u - cx) * Z / fx
Y = (v - cy) * Z / fy
```

每个成功匹配的像素得到一个 `(X, Y, Z)` 点，全部三维点组成点云。近处目标的视差较大，通常更容易测准；目标越远，视差越小，同样的像素匹配误差会造成更大的深度误差。

普通双目的优势是成本较低、覆盖面积大、采集速度快，不需要主动投射图案。它的核心弱点是依赖表面自身纹理。大面积纯色、黑色、透明或高反光表面很难建立可靠的左右对应关系，常见结果是空洞、飞点、边缘撕裂，甚至 RGB 图像正常但深度全部无效。因此它更适合粗定位、避障和中低精度建模，不宜单独承担高精度打磨余量测量。

### 11.2 结构光面阵相机

结构光相机向工件表面主动投射已知条纹、散斑或编码图案，再由一个或多个相机观察图案变形，通过三角测量恢复深度。主动投影给低纹理表面增加了可识别特征，因此点云通常比普通被动双目更密、更稳定。

结构光面阵一次曝光可以覆盖一整片区域，机器人在多个固定站位采集后即可拼接大面积表面，兼顾效率、点密度和精度。Mech-Eye NANO ULTRA-GL 属于蓝光结构光 3D 相机，适合机器人近距离采集、工件定位和多站表面重建。

它仍会受到材料和环境影响：

- 黑色表面吸收投射光，返回信号较弱。
- 高亮漆面产生镜面反射，条纹可能过曝或偏离接收镜头。
- 透明或半透明材料会发生折射和内部散射。
- 强环境光可能淹没投射图案。
- 曲率大、遮挡严重的区域需要增加采集视角。
- 视野扩大和工作距离增加时，横向点间距和深度精度通常都会下降。

因此，厂商给出的单点重复性或 VDI/VDE 精度不能直接等同于整车重建精度。正式验收应在真实颜色、光泽、距离、入射角和环境光条件下，统计有效点比例、重复性以及多站拼接残差。

### 11.3 激光线扫相机

激光线扫传感器向表面投射一条激光线，相机利用三角测量得到这条线上的二维轮廓。机器人、直线模组或工件连续运动时，多条轮廓按运动位姿依次拼接，形成完整三维表面。

激光线扫的单条轮廓精度通常最高，适合恢复小凹坑、小凸起、焊缝、接缝、边缘和局部曲率变化，也更适合计算精细打磨余量。但它一次只能获得一条轮廓，因此系统对运动质量要求很高：

- 每条轮廓必须绑定准确的位置和时间戳。
- 扫描速度变化会改变相邻轮廓间距。
- 机器人振动、回差和绝对定位误差会形成波纹或错层。
- 传感器与机器人之间的手眼标定误差会累积到整片点云。
- 仅使用机器人控制器低频反馈位姿，往往不足以支撑高精度线扫。

工程上常使用编码器硬件触发、高精度直线轴或外部跟踪系统，使轮廓采样与运动位置严格对应。传感器标称达到微米级，并不意味着机器人带着它扫描后仍能获得微米级整面精度。

### 11.4 三种方案的工程对比

| 维度 | 普通被动双目 | 结构光面阵 | 激光线扫 |
| --- | --- | --- | --- |
| 单次覆盖 | 大 | 大 | 一条轮廓 |
| 点云密度 | 中，依赖纹理 | 高 | 沿线高，扫描方向取决于运动步距 |
| 典型精度潜力 | 较低 | 中高 | 最高 |
| 采集效率 | 高 | 中高 | 较低 |
| 对自身纹理依赖 | 高 | 低 | 低 |
| 对反光/黑色表面 | 较敏感 | 敏感 | 仍敏感，但可通过波长、功率和滤光优化 |
| 对机器人运动精度依赖 | 静止拍摄时较低 | 静止拍摄时较低 | 很高 |
| 系统集成复杂度 | 低 | 中 | 高 |
| 典型用途 | 避障、粗定位、粗建模 | 工件定位、多站重建、尺寸检测 | 精密轮廓、缺陷、焊缝和余量检测 |

### 11.5 最终精度是一条误差链

高精度重建不能只看传感器参数。整套系统的最终误差可近似理解为：

```text
最终误差 ≈ 传感器测量误差
         + 相机内参误差
         + 手眼标定误差
         + 机器人/运动轴位姿误差
         + 时间同步误差
         + 多站配准误差
         + 支架变形、振动和温漂
```

对于面阵相机，机器人通常停稳后采集，运动误差主要表现为站位和手眼变换误差；对于激光线扫，机器人在采集过程中持续运动，位姿和时间同步误差会直接进入每一条轮廓，因此更难把传感器自身的高精度兑现为整面精度。

### 11.6 客车表面打磨场景的选择

客车车身面积大、曲面多，且常有纯色、黑色和高亮漆面。若目标是生成打磨规划所需的整车表面，结构光面阵通常是精度、覆盖范围、节拍和集成难度之间更实际的选择：机器人停稳后多站采集，再通过可靠的手眼变换和配准合成整车表面。

若目标是检测亚毫米级局部缺陷、焊缝轮廓或精确计算局部打磨余量，激光线扫更有优势，但需要同步解决编码器触发、扫描轨迹、速度稳定性、标定和振动问题。普通双目可用于粗定位、避障和辅助识别，不应在缺少真实材质验证时承担高精度重建主链路。

一种更稳妥的组合方案是：

```text
结构光面阵：完成大面积、多站快速重建
激光线扫：补测焊缝、边缘、缺陷和高精度区域
普通双目：承担粗定位、避障和场景理解
```

选型时应先定义允许误差、最小缺陷尺寸、单车节拍和可接受空洞率，再使用真实车身样件做对比测试。只比较厂商规格表中的“最高精度”，无法判断哪种方案能在现场稳定工作。
